## وضعیت و مرز نتیجه

- **M0-A:** تثبیت مرجع، استخراج مراحل محاسبه، دروازهٔ سازگاری و تست‌های مهندسی.
- **M0-B:** تولید checkpoint آموزش‌دیده با پروتکل اصلی روی CUDA.
- این ماشین GPU مناسب CUDA در اختیار ندارد؛ نتایج مهندسی، نتیجهٔ آموزش مقاله نیستند.
- فایل `runs/m0/untrained_fixture.pt` صریحاً آموزش‌ندیده است.
- گزارش اجرا در `docs/M0_REPORT_FA.md` و گزارش ماشینی در `runs/m0/` است.

## اجرای تست‌ها در PowerShell

از همین پوشه:

```powershell
.venv/Scripts/python.exe -B scripts/run_m0.py
```

این فرمان سه مرحله را در فرایندهای جدا اجرا می‌کند: ممیزی مرجع و داده، تمام تست‌های
مرجع، سپس تست‌های پژوهشی. لاگ و JUnit در `runs/m0/` ذخیره می‌شود. اگر محیط محدود
Windows دسترسی پوشهٔ موقت را رد کند، همین فرمان باید با مجوز اجرای لازم اجرا شود؛
کد و تست مرجع نباید برای پنهان‌کردن خطای مجوز تغییر کنند.

## ساخت محیط روی ماشین دیگر

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-m0.lock.txt
```

فایل lock وضعیت محیط CPU فعلی را ثبت می‌کند. برای میزبان GPU باید PyTorch سازگار
با CUDA آن میزبان نصب و محیط تازه ثبت شود؛ برابری بین دو سخت‌افزار ادعا نمی‌شود.
نوت‌بوک `notebook/M0_Reference_Training.ipynb` از سیاست سازگاری بستهٔ اصلی استفاده می‌کند.

## آموزش مرجع روی CUDA

```powershell
.venv/Scripts/python.exe -B scripts/run_reference_training.py --mode single
.venv/Scripts/python.exe -B scripts/run_reference_training.py --mode four
```

حالت `single` همان پروفایل ثبت‌شدهٔ تک‌بذر برای مرجع مهندسی است؛ حالت `four` مطالعهٔ
چهاربذری اصلی را اجرا می‌کند. هیچ بذر، آستانه یا دستور آموزش در این launcher تغییر
نمی‌کند. در نبود CUDA فرمان با توضیح روشن متوقف می‌شود و checkpoint ساختگی نمی‌سازد.

## نکات طراحی

۱. `ResearchModel` یک نمونهٔ مرجع را نگه می‌دارد. در حالت غیرفعال یا coupling صفر،
مستقیماً همان مدل فراخوانی می‌شود؛ پارامتر فاز یا probe اضافه‌ای وجود ندارد.

۲. `SteppedNative` مسیر بازآرایی‌شدهٔ مستقل برای آزمایش و توسعهٔ بعدی است. شیء
substrate پس از همان سازندهٔ اصلی به زیرکلاسِ بدون پارامتر جدید تبدیل می‌شود؛
این کار از مقداردهی اولیهٔ دوباره و مصرف RNG جلوگیری می‌کند و تست مستقل دارد.

۳. خروجی legacy `phi` دست‌نخورده است. `phase_adhesion` و اصلاح هندسه متعلق به
مراحل بعدند و در M0 خروجی ساختگی برای آن‌ها تولید نشده است.

۴. checkpoint پژوهشی در مرز پایان optimizer step ذخیره می‌شود؛ ذخیره در میانهٔ
gradient accumulation پشتیبانی نمی‌شود. فایل checkpoint باید قابل‌اعتماد باشد.

۵. ابزار ذخیرهٔ جدید، فرمت checkpoint قدیمی را به‌عنوان ادامهٔ کامل تلقی نمی‌کند.
checkpoint قدیمی برای وزن‌های مرجع مفید است؛ RNG ازدست‌رفته را نمی‌توان بازسازی کرد.
اجرای رسمی M0-B عمداً از مکانیزم resume اصلی خودش استفاده می‌کند و این تفاوت باید
در هر ادعای تکرارپذیری حفظ شود.

۶. `bootstrap_m0.py` ابزار استخراج اولیه است. اجرای دوباره‌اش `native_steps.py`
را بازتولید می‌کند؛ پس از شروع تغییرات پژوهشی، آن را روی فایل‌های ویرایش‌شده اجرا نکنید.
