# آزمون اطلاعات context در M2

## نتیجه

برای تعیین اینکه مشکل از نبود اطلاعات است یا از ظرفیت anchor، یک طبقه‌بند خطی
روی ویژگی‌های endpoint اجرا شد. این طبقه‌بند فقط ابزار اندازه‌گیری است و وارد
forward یا تصمیم native نمی‌شود.

| ویژگی ورودی | دقت متوازن پایش | کنترل برچسب تصادفی |
|---|---:|---:|
| `Psi0` مستقل | ۳۲٫۳۱٪ | ۳۵٫۵۳٪ |
| context نهایی native | ۴۱٫۴۲٪ | ۳۳٫۳۳٪ |
| کل تاریخچهٔ چهار حالت میدان | **۴۲٫۳۱٪** | ۲۹٫۴۰٪ |

حد شانس برای سه رابطه ۳۳٫۳۳٪ است. بنابراین context واقعاً اطلاعاتی دربارهٔ رابطه
دارد، اما اطلاعات آن ضعیف است و به حد ۷۰٪ لازم برای readiness نمی‌رسد.

## طراحی

همان تقسیم M2 استفاده شد: ۳۸۲ نمونهٔ fit و ۱۲۲ نمونهٔ پایش، با ۳۴۸۰ و ۱۰۶۴
رویداد. برای هر رویداد ویژگی‌های مبدأ، مقصد، قدرمطلق اختلاف و حاصل‌ضرب آن‌ها
ساخته شد. در حالت تاریخچه، این ویژگی برای حالت اولیه و سه گام کامل میدان پشت‌سرهم
قرار گرفت. آموزش طبقه‌بند ۴۰ دوره بود و یک اجرای جداگانه با برچسب‌های درهم‌ریخته
به‌عنوان کنترل انجام شد.

این آزمون از دادهٔ validation، tuning یا افق نهایی استفاده نکرد. هیچ وزن native
تغییر نکرد و هیچ پاسخ native از probe گرفته نشد.

## برداشت

`Psi0` محلی تقریباً رابطه را نمی‌بیند؛ context native اطلاعات رابطه را به endpoint
منتقل می‌کند و نتیجه از شانس بالاتر است. افزودن تمام تاریخچه فقط کمی بهتر از context
نهایی است؛ پس افزایش سادهٔ snapshotها کافی نیست. برای کالیبراسیون باید یا context
قوی‌تر شود، یا یک نمایش جفتی/رابطه‌ای با regularization و دادهٔ بیشتر طراحی شود.

نتیجهٔ encoder جفت قبلی روی fit برابر ۶۶٫۸۴٪ و روی پایش ۳۹٫۲۰٪ بود؛ بخشی از ظرفیت
آن حفظ‌کردن دادهٔ fit است. این آزمون هم‌زمان کمبود اطلاعات و ضعف تعمیم را نشان می‌دهد.

## تصمیم

M2 و M3 همچنان پذیرفته نشده‌اند. فعال‌کردن فاز در geometry در این وضعیت انجام نمی‌شود.
گام بعدی مجاز، آزمایش کنترل‌شدهٔ context تقویت‌شده است؛ اگر پایش به آستانه نرسد،
محدودیت معماری ثبت و پروژه در M2 متوقف می‌ماند.
