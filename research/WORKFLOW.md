# قرارداد چرخهٔ آزمایش و Colab

این چرخه اجرای [برنامهٔ عملیاتی](../docs/OPERATIONAL_ROADMAP_FA.md) را قابل پیگیری می‌کند. ساخت زیرساخت یا آماده‌شدن نوت‌بوک، اجرای Colab یا پذیرش فاز محسوب نمی‌شود. مرجع مسیرها [INDEX](INDEX.md) و مسئولیت ایجنت [AGENTS](../AGENTS.md) است.

## واحدهای کار و نسخه‌بندی

- **فاز** یک هدف و مجموعهٔ دروازه‌های سند است؛ ممکن است چندین آزمایش و شاخه لازم داشته باشد.
- **آزمایش** یک سؤال علمی/مهندسی مشخص با شناسهٔ ثابت، برای مثال `m2-q-checkpoint` است.
- **نسخه** (`v001`، `v002`، ...) یک ترکیب مشخص از پروتکل، کد علمی و نوت‌بوک است. پس از بسته‌بندی/اجرا، تغییر آن‌ها نسخهٔ تازه می‌گیرد. تصحیح توضیح نتیجه بدون تغییر شاهد باید رویداد اصلاحی داشته باشد.
- **run** یک اجرای مشخص همان نسخه با شناسهٔ یکتا است؛ اجرای دوباره یا seed جدید run جدا دارد. اگر seed خارج از برنامهٔ قفل‌شده باشد، پروتکل نسخهٔ تازه لازم دارد.
- **شاخه** سؤال یا راهبرد جایگزین است. شناسهٔ آزمایش تازه می‌گیرد و به نسخه/run والد و ADR مربوط پیوند می‌خورد؛ هیچ مسیر منفی حذف نمی‌شود.
- **artifact** فایل حجیم مانند checkpoint است. خود فایل محلی/خارجی نگهداری و نشانی، hash و اندازهٔ آن در ریپو ثبت می‌شود.

مراحل مفهومی چرخه چنین‌اند؛ نام‌های وضعیت ماشینی را schema و CLI تعیین می‌کنند:

```text
طرح ثبت‌شده → کد و تست → نوت‌بوک/بستهٔ معتبر → منتظر Colab
  → نتیجهٔ واردشده → تحلیل و بازبینی
       → pass: بررسی تمام دروازه‌های فاز و سپس پیشروی
       → revise: نسخه یا شاخهٔ تازه با parent و دلیل
       → inconclusive: تکمیل شاهد یا تکرار مشخص
```

برای یک خطای runtime نیز bundle تا حد ممکن دریافت شود. قطع اجرا، artifact مفقود و دادهٔ نامعتبر نتیجهٔ علمی منفی نیستند؛ نوع شکست را جدا ثبت کنید.

## تعریف دقیق «آمادهٔ اجرا»

پروتکل باید پیش از اجرای اصلی این موارد را روشن کند:

1. سؤال، فرضیه و نتیجه‌ای که آن را رد می‌کند؛ بخش سند و ADR مرتبط.
2. آزمایش/نسخه/run والد، تفاوت این تلاش و علت انتخاب آن.
3. commit/snapshot و hash سورس؛ فرمان اجرا و config؛ dependencyهای لازم.
4. seedها، منشأ و hash داده، splitهای fit/monitor/test و تاریخچهٔ دیده‌شدن آن‌ها؛ موارد جلوگیری از leakage.
5. ورودی‌ها و checkpointهای لازم با hash و روش دریافت؛ secrets داخل نوت‌بوک قرار نگیرند.
6. metricها، کنترل‌ها، آستانه‌ها، پنجره‌های پذیرش و معیار توقف؛ تفاوت معیار run و معیار فاز.
7. GPU/RAM موردنیاز، بودجهٔ اجرا و تخمین زمان یا برچسب «هنوز اندازه‌گیری نشده».
8. فایل‌های خروجی اجباری، checkpoint منتخب/ادامه، روش resume و روش بسته‌بندی نتیجه حتی در شکست.
9. نقش آزمایش: smoke، اکتشافی، کالیبراسیون، یا تأییدی مستقل؛ ادعاهای مجاز و غیرمجاز.

تست محلی باید با سؤال تغییر تناسب داشته باشد. تست‌های بازیابی، هویت bundle و جلوگیری از overwrite برای خود چرخه لازم‌اند؛ اجرای سریع جای آزمون علمی اصلی را نمی‌گیرد.

## توضیح داخل نوت‌بوک

نوت‌بوک باید بدون اتکا به حافظهٔ گفتگو قابل فهم باشد: هویت آزمایش و نسخه، هدف، ارتباط با تلاش قبلی، پیش‌نیاز، هزینه، آنچه هر مرحله انجام می‌دهد و آنچه نتیجه می‌تواند اثبات کند در سلول‌های Markdown درج شود. مراحل استاندارد:

1. معرفی و خواندن پروتکل قفل‌شده.
2. دریافت بستهٔ منبع و راستی‌آزمایی hashها.
3. آماده‌سازی محیط و ثبت Python/کتابخانه‌ها/GPU/CUDA.
4. یافتن و بررسی داده و checkpointهای ورودی.
5. کنترل‌های اولیه و توضیح معیار توقف.
6. اجرای runner؛ ثبت log، وضعیت خروج و زمان.
7. گزارش metricها و فایل‌های تولیدشده با محدودیت تفسیر.
8. ساخت bundle بازگشت با checksum و ذخیره در محل ماندگار/دانلود.
9. دستور دقیق بازگرداندن فایل به `research/inbox/` و اعلام شناسه به ایجنت.

کد علمی در `ergt_phi/` و `scripts/` نگه داشته شود. تغییر دستی سلول علمی در Colab، اجرای ثبت‌شدهٔ همان نسخه نیست؛ آن را ثبت و برای استفادهٔ رسمی نسخهٔ تازه تولید کنید. فایل منبع `.ipynb` بدون خروجی حجیم در Git باشد؛ اگر نوت‌بوک اجراشده نگهداری می‌شود، artifact run است و جای منبع را نمی‌گیرد.

پس از سامان‌دهی، بستهٔ سورس جدید نقشهٔ مسیرهای legacy و دو metadata کوچک مرجع/M0
را نیز با hash شامل می‌شود. checkpoint، protocol/data_manifest اجرای ورودی و دادهٔ
لازم باید همچنان در `inputs` با مسیر canonical، هش و محل دریافت صریح ثبت شوند.
`research/artifacts/` به‌طور خودکار وارد ZIP سورس نمی‌شود. بسته‌های قبلاً قفل‌شده
از این تغییر بازنویسی نمی‌شوند و از ZIP یا commit اصلی خود قابل بازیابی‌اند.

## قرارداد دریافت و ورود نتیجه

پژوهشگر ZIP نتیجه را در `research/inbox/` می‌گذارد یا مسیر دقیق آن را می‌دهد. ایجنت در نوبت بعدی آن را بررسی می‌کند؛ این روش پایش پیوستهٔ Drive/Colab نیست. اجرای از راه دور فقط با اتصال واقعی و مجاز قابل نسبت‌دادن به ایجنت است.

ورود نتیجه باید هویت آزمایش، نسخه و run؛ hash پروتکل و snapshot؛ checksum فایل‌ها؛ وضعیت اجرا و محیط را بررسی کند. ZIP فقط در محل تعیین‌شده باز شود؛ مسیر مطلق، `..`، نام متعارض و overwrite خروجی موجود پذیرفته نشوند. checkpoint ناشناس اجرا یا با بارگذاری ناامن بررسی نشود. وزن‌ها به محل artifact منتقل و فقط متادیتای لازم وارد Git شوند.

برای بازگشت بدون تمام خروجی‌ها، نتیجه «ناقص/نیازمند بررسی» باقی می‌ماند. فایل‌های summary، log، environment و metadata باید کنار run حفظ شوند و گزارش انسانی به آن‌ها لینک بدهد. `summary.md` خروجی تولیدشدهٔ معیارهاست و بازنویسی نمی‌شود؛ تحلیل علمی با قالب [interpretation](templates/interpretation.md) در `interpretation.md` همان run نوشته می‌شود. اگر بسته/چک‌سام نامعتبر است، اصل ورودی محفوظ بماند و علت عدم پذیرش ثبت شود.

نشانی آرشیو با `import --source-uri` در `artifacts.json` ثبت می‌شود. افزودن نشانی به run قبلاً واردشده، رکورد افزایشی `locations/001.json` می‌سازد. این نشانی به‌تنهایی اثبات دسترسی به Drive نیست؛ `remote_availability_verified=false` همین محدودیت را مشخص می‌کند. برای checkpointهای لازم، نسخهٔ ماندگار نتیجه و hash آن باید حفظ شود.

## قالب محتوایی گزارش هر run

گزارش علمی `interpretation.md` باید سؤال، شناسه‌ها، نسخه/commit، محیط، ورودی‌ها، روش و کنترل‌ها را مشخص کند و به `summary.md` و `run.json` پیوند بدهد. مقدار هر metric کنار آستانهٔ پیش از اجرا بررسی شود. جدول تفسیر حداقل ستون‌های «معیار»، «انتظار»، «مشاهده»، «شاهد» و «وضعیت» دارد؛ دادهٔ خام و خلاصهٔ تولیدشدهٔ اولیه دست‌نخورده می‌مانند.

در ادامه علت محتمل، عدم قطعیت، دادهٔ منفی، هزینه، نشانی و hash checkpoint، صحت load/resume، محدودیت تعمیم و تفاوت با run والد نوشته شود. پایان گزارش شامل داوری `pass`/`revise`/`inconclusive`، دامنهٔ همان داوری، قدم بعد، ADR مربوط و اثر بر ادعاهای مقاله باشد. خروج موفق فرایند به‌تنهایی هیچ آستانهٔ علمی را پاس نمی‌کند.

CLI داوری را در `runs/<run_id>/reviews/001.json` ثبت می‌کند. بازنگری آن نیازمند ADR جدید و رکورد بعدی است؛ تاریخچه محفوظ می‌ماند. `evaluation.json` شرایط عددی را می‌سنجد، ولی ورود به فاز بعد با CLI خودکار انجام نمی‌شود.

## بازبینی فاز و تغییر هدف

پیش از ورود به فاز بعد، مدارک تمام دروازه‌های [roadmap](../docs/OPERATIONAL_ROADMAP_FA.md) بررسی شوند. ایجنت این پرسش‌ها را در گزارش فاز پاسخ دهد:

- این نتیجه کدام بخش هدف ریاضی را پشتیبانی یا تضعیف می‌کند؟
- آیا پیش‌فرض معماری، داده یا هزینه تغییر کرده است؟
- چه کنترل یا آزمایش تمایزبخشی بین توضیح‌های رقیب لازم است؟
- ادامهٔ شاخه، برگشت، شاخهٔ جایگزین یا توقف کدام دلیل و هزینه را دارد؟
- آیا تعریف موفقیت تغییر می‌کند؟ اگر بله، ADR، نسخهٔ spec/addendum و برنامهٔ تازه کدام‌اند؟

پیشنهاد بازنگری هدف باید شواهد و پیامدش را روشن کند و مطابق دامنهٔ مجوز با پژوهشگر بحث شود. اجرای گذشته با هدف جدید «پاس» نامیده نشود. سند پایه محفوظ می‌ماند و افزونه/نسخهٔ تازه تفاوت را بیان می‌کند.

هدف و دامنهٔ نسخه‌دار در [goals.json](goals.json) و بازبینی هر فاز در `research/phase_reviews/` ثبت شود؛ [M2_CURRENT.md](phase_reviews/M2_CURRENT.md) نقطهٔ شروع فعلی است. قالب‌های [پروتکل](templates/protocol.json)، [تحلیل](templates/interpretation.md)، [تصمیم](templates/decision.md) و [بازبینی فاز](templates/phase_review.md) اقلامی را که نباید فراموش شوند مشخص می‌کنند. خلاصهٔ ماشینی معیارها جای تحلیل علت و تصمیم علمی را نمی‌گیرد.

## پیگیری و ثبت Git

پایان هر milestone، STATE و registry باید وضعیت، مانع واقعی و مالک قدم بعد را نشان دهند. انتظار برای Colab به‌طور مشخص «اقدام پژوهشگر» است؛ آماده‌سازی یا تحلیل «اقدام ایجنت» است. ایجنت در نوبت بعد ورودی تازه را بررسی و فقط یادآوری لازم را مطرح می‌کند.

نقاط commit معمول: پروتکل/طرح ثبت‌شده؛ کد و تست معتبر؛ نسخهٔ نوت‌بوک؛ قفل بسته و inventory؛ ورود نتیجهٔ معتبر؛ تحلیل و تصمیم؛ بازنگری برنامه. عملیات هم‌بسته می‌توانند یک commit داشته باشند. برای بستهٔ علمی، commit شامل کد/پروتکل/نوت‌بوک باید پیش از بسته‌بندی انجام شود تا HEAD داخل بسته منبع قابل بازیابی باشد. هر commit باید تغییر واقعی و بررسی‌شده باشد؛ صرف تغییر وضعیت به امید اجرای آینده پیشرفت علمی نیست.

قبل از commit، diff و فایل‌های staged بررسی شوند. ZIP، وزن و artifact حجیم، اطلاعات خصوصی و تغییر نامرتبط وارد نشود. بدون مجوز انتشار، push انجام نشود. برای اجرای Colab، hash snapshot و protocol مرجع قطعی هستند؛ اگر بسته از یک working tree غیرتمیز ساخته شده است این موضوع صریح ثبت شود و به اشتباه آن را برابر یک commit تمیز معرفی نکنید.

## بازیابی منبع یک اجرای قدیمی

`source_manifest.json` در پوشهٔ همان نسخه، فهرست دقیق فایل‌های بسته و hash آن‌ها را نگه می‌دارد و hash خود inventory داخل `package.json` قفل می‌شود. این دو فایل tracked هستند؛ ZIP در `research/packages/` نیست. اگر ZIP محلی مفقود شد، `package --id ... --revision ...` تنها با همان فایل‌های دقیق، آرشیو با hash قبلی را بازسازی می‌کند؛ با سورس جدید حق تغییر بستهٔ قدیمی را ندارد.

برای بازیابی پس از تغییر پروژه، نسخهٔ منبع ثبت‌شده را در checkout جدا باز کنید، inventory را تطبیق دهید و بسته را بسازید یا ZIP اصلی را از بایگانی ثبت‌شده بگیرید. HEAD پایهٔ یک snapshot غیرتمیز الزاماً همهٔ فایل‌های داخل بسته را ندارد. اگر نمونهٔ زیرساختی از چنین snapshotی ساخته شد، commit بعدیِ حاوی همان bytes یا نشانی ZIP اصلی باید در گزارش/رویداد ثبت شود؛ inventory به‌تنهایی محتوای فایل مفقود را تولید نمی‌کند.

پشتیبان ZIP سورس و ZIP نتیجه نقش‌های جدا دارند؛ نشانی هر دو، hash و وضعیت بازیابی آن‌ها ثبت شود. ثبت URI در ابزار به معنی بررسی خودکار دسترس‌پذیری آن نیست. یادآور فعلیِ CLI همهٔ اقلام انسانی مانند تکمیل تفسیر، بازبینی هدف و بایگانی سورس را الزاماً بررسی نمی‌کند؛ ایجنت علاوه بر `status` چک‌های [AGENTS](../AGENTS.md) را انجام می‌دهد.

## آماده‌سازی مقاله

برای هر نتیجه، [CLAIMS](CLAIMS.md) باید ادعا، شاهد مستقیم، کنترل، نوع split، seed، دامنهٔ اعتبار و محدودیت را نگه دارد. جدول/نمودار باید از دادهٔ ثبت‌شده قابل تولید باشد و runهای منفی مرتبط هم ذکر شوند. آزمایش‌های تأییدی پس از تثبیت پروتکل روی دادهٔ بازنشده اجرا شوند؛ گزینش بهترین run بدون ثبت سایر تلاش‌ها مجاز نیست.

پس از ورود/بازبینی run، `python -B scripts/export_research_catalog.py` فهرست [RUN_CATALOG](paper/RUN_CATALOG.md) و [evidence.csv](paper/evidence.csv) را بازتولید می‌کند. این خروجی‌ها باید همراه milestone بررسی و commit شوند؛ مقادیر تولیدشده به‌جای سند run به‌صورت دستی اصلاح نشوند.

## فرمان‌های عملیاتی

فرمان‌ها از ریشهٔ ریپو و در ترمینال اجرا می‌شوند؛ در PowerShell محیط پروژه می‌توان `python` را با `.\.venv\Scripts\python.exe` جایگزین کرد. برای تشخیص کار جاافتاده در آغاز و پایان نوبت:

```powershell
python -B scripts/research.py status --json
```

نمونهٔ زیر الگوی یک آزمایش آینده است؛ `M2-E002`، فایل config، run و ADR باید با رکورد واقعی جایگزین شوند. تا runner و پروتکل واقعاً آماده نشده‌اند این فرمان‌ها به‌معنی تحویل M2 نیستند:

```powershell
python -B scripts/research.py create --protocol configs/m2_e002_v001.json
python -B scripts/research.py notebook --id M2-E002 --revision v001
```

قالب `research/templates/protocol.json` ابتدا با runner واقعی، تمام ورودی‌ها، تاریخ، فرضیه و gateهای کامل در config پر می‌شود. نوت‌بوک در مسیر نسخه ساخته می‌شود. پس از بررسی و commit فایل‌های source/protocol/notebook، بسته ساخته و قفل و inventory آن نیز commit شوند:

```powershell
python -B scripts/research.py package --id M2-E002 --revision v001
```

ZIP آپلود در `research/packages/` است. پس از اجرای واقعی Colab، نتیجه وارد شود؛ `--source-uri` نشانی نسخهٔ پشتیبان ماندگار است و ابزار دسترس‌پذیری آن در اینترنت را تأیید نمی‌کند:

```powershell
python -B scripts/research.py import research/inbox/RESULT.zip --source-uri "drive://PATH_OR_FILE_ID"
```

ایجنت `summary.md` و `evaluation.json` را می‌خواند، `interpretation.md` را می‌نویسد و ADR مرتبط را می‌سازد. سپس با دلیل واقعی داوری را ثبت می‌کند. مثال زیر فقط قالب فرمان است؛ همهٔ مقدارهای `REPLACE` باید از شاهد واقعی بیایند:

```powershell
python -B scripts/research.py review --id M2-E002 --revision v001 --run-id REPLACE_RUN_ID --decision inconclusive --decision-id ADR-0002 --reason "REPLACE_WITH_EVIDENCE_BASED_REASON" --next-action "REPLACE_WITH_CONCRETE_NEXT_ACTION"
```

اگر اصلاح لازم بود، config تازه باید `revision=v002`، والد و دلیل تغییر را داشته باشد؛ نسخهٔ بسته‌شدهٔ قبلی تغییر نمی‌کند:

```powershell
python -B scripts/research.py revise --id M2-E002 --from v001 --protocol configs/m2_e002_v002.json --reason "REPLACE_WITH_REVISION_REASON"
```

برای milestoneهایی مثل ثبت بحث یا تکمیل کد، رویداد مرتبط ثبت شود و بعد diff و فایل‌های انتخاب‌شده commit شوند. خود CLI به‌جای ایجنت تحلیل علمی یا commit انجام نمی‌دهد:

```powershell
python -B scripts/research.py event --type milestone --message "REPLACE_WITH_VERIFIED_PROGRESS" --path research/STATE.md
```
